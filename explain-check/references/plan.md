# plan: 설계 방향을 정한 직후, 코딩 전

결과물: `EXPLAIN.md`의 "설계" 섹션. 한 화면(40줄 안팎)을 넘기지 않는다.
이 섹션은 작업 기준이자, 질의응답이나 발표에서 사용자가 설명할 재료가 된다.

## EXPLAIN.md 형식

```
# EXPLAIN
## 설계
### 1. 문제 (현업 언어로)
### 2. 성공 기준과 완료 조건
### 3. 방식 비교와 선택
### 4. 위험
### 5. 예외와 데이터 보호
### 6. 담당자에게 확인할 것
### 7. 설명 질문
## 결정
## 근거
## 방어 노트
```

## 각 항목에 쓸 것

1. **문제**: 누가, 무엇 때문에 곤란하고, 지금은 어떻게 하고 있고, 그 손해가 얼마인지. 확인되지 않은 내용은 6번으로 보낸다.
2. **성공 기준과 완료 조건**
   - 결과 지표 2~3개와 목표값
   - 기준선: 가장 단순한 방식이나 현재 방식으로 냈을 때의 지표 값. 아직 모르면 처음 측정할 대상으로 적는다.
   - 완료 조건: 무엇이 실행되고 어떤 값이 나오면 끝인지
3. **방식 비교와 선택** (사용자 결정)
   - 방식 2개를 비교한다. 각각의 장점, 포기하는 것, 사용자가 설명하기 쉬운 정도를 적는다.
   - 사용자가 고르게 한다. 비슷하면 설명하기 쉬운 쪽을 권한다.
   - 고른 방식에 대한 가장 강한 반론 한 줄과 그에 대한 답을 남긴다.
4. **위험** (사용자 결정)
   - "이 결과물이 현장에서 실패했다면 왜일까?"를 기준으로 위험 3~5개를 찾는다.
   - 각각 Tiger(대책 없으면 실제 피해), Paper(위험해 보이지만 괜찮음, 이유 한 줄), Elephant(드러나지 않았지만 중요한 우려) 중 하나로 표시한다.
   - Tiger는 대책을 세울지 수용할지 사용자가 정한다. 대책은 작업 계획에 단계로 넣는다.
5. **예외와 데이터 보호**: 예외 상황(빈 입력, 잘못된 값, 제약 위반, 후보 없음 등)마다 기대 동작을 정한다. 실패했을 때 기존 데이터를 어떻게 지킬지 정한다.
6. **담당자에게 확인할 것**: 1~5에서 추정으로 채운 부분 중 결과를 바꿀 수 있는 것만 질문으로 만든다. 많아도 5개.
7. **설명 질문**: 이 프로젝트에 맞춘 질문 5개. 설계 선택, 검증 범위, 동작과 예외, 가장 약한 지점, AI와 함께 내린 결정에서 하나씩.
