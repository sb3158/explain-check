# plan: 설계를 시작할 때, 코딩 전

인터뷰와 합의가 끝난 뒤, 설계 방식을 정하기 전에 부른다.
결과물: `EXPLAIN.md`의 "설계" 섹션(40줄 안팎). 작업 기준이자, 사용자가 질의응답에서 설명할 재료다.

## 순서

1. 아래 1~3번을 쓰고 방식을 고르게 한다 **(결정)**. 사용자가 이미 방식을 정했다면 가장 가까운 대안 하나와의 비교만 기록하고 넘어간다.
2. 고른 방식으로 4~8번을 쓴다. Tiger 위험은 대응안을 붙여 한 번에 묻는다 **(결정)**.
3. 아래 AGENTS.md 블록을 넣는다.

## EXPLAIN.md 뼈대

```
# EXPLAIN
## 설계        (아래 1~8을 ### 소제목으로)
## 결정
## 근거
## 방어 노트
```

## 설계 항목

1. **문제**: 누가, 무엇 때문에 곤란하고, 지금은 어떻게 하고 있고, 그 손해가 얼마인지. 확인되지 않은 내용은 7번으로 보낸다.
2. **성공 기준과 완료 조건**
   - 결과 지표 2~3개와 목표값
   - 기준선: 가장 단순한 방식이나 현재 방식의 지표 값. 모르면 처음 측정할 대상으로 적는다.
   - 완료 조건: 무엇이 실행되고 어떤 값이 나오면 끝인지. 화면이 있으면 주요 버튼과 입력이 실제로 동작하는 것을 포함한다.
3. **방식 비교와 선택**: 방식 2개의 장점, 포기하는 것, 큰 위험, 설명하기 쉬운 정도를 비교하고 하나를 추천한다(비슷하면 설명하기 쉬운 쪽). 고른 뒤에는 그 방식에 대한 가장 강한 반론 한 줄과 답을 남긴다.
4. **위험**: "현장에서 실패했다면 왜일까?"로 3~5개를 찾아 Tiger(대책 없으면 실제 피해), Paper(위험해 보이지만 괜찮음, 이유 한 줄), Elephant(드러나지 않았지만 중요한 우려)로 표시한다. 대책을 세우기로 한 Tiger는 작업 단계로 넣는다.
5. **예외와 데이터 보호**: 예외 상황(빈 입력, 잘못된 값, 제약 위반, 후보 없음 등)마다 기대 동작을 정하고, 실패했을 때 기존 데이터를 어떻게 지킬지 정한다.
6. **구조 (모듈 지도)**: 모듈이나 파일(많아야 8개)마다 맡은 일 한 줄. 입력 하나가 결과가 되는 경로(`파일:함수` 순서), 데이터가 어디에 저장되고 누가 바꾸는지. 계산·판정 같은 핵심 로직은 화면 코드와 분리한다.
7. **담당자에게 확인할 것**: 1~6에서 추정으로 채운 것 중 결과를 바꿀 수 있는 것만, 많아도 5개.
8. **설명 질문**: 이 프로젝트에 맞춘 질문 6개. 설계 선택, 구조와 데이터 흐름, 검증 범위, 동작과 예외, 가장 약한 지점, AI와 함께 내린 결정에서 하나씩.
