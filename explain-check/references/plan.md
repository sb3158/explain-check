# plan: 설계를 시작할 때, 코딩 전

인터뷰와 합의가 끝난 뒤, 설계 방식을 정하기 전에 부른다.
결과물: `EXPLAIN.md`의 "설계" 섹션(55줄 안팎). 작업 기준이자, 사용자가 질의응답에서 설명할 재료다.

## 순서

1. 아래 1~3번을 쓰고 방식을 고르게 한다 **(결정)**. 사용자가 이미 방식을 정했다면 가장 가까운 대안 하나와의 비교만 기록하고 넘어간다.
2. 고른 방식으로 4~9번을 쓴다. Tiger 위험은 대응안을 붙여 한 번에 묻는다 **(결정)**.
3. 아래 AGENTS.md 블록을 넣는다.

## EXPLAIN.md 뼈대

```
# EXPLAIN
## 설계        (아래 1~9를 ### 소제목으로)
## 결정
## 근거
## 방어 노트
```

## 설계 항목

1. **문제**: 누가(실제로 쓸 사람과 그 사람의 숙련도), 무엇 때문에 곤란하고, 지금은 어떻게 하고 있고, 그 손해가 얼마인지. 확인되지 않은 내용은 8번으로 보낸다.
2. **성공 기준과 완료 조건**
   - 결과 지표 2~3개와 목표값
   - 기준선: 가장 단순한 방식이나 현재 방식의 지표 값. 모르면 처음 측정할 대상으로 적는다.
   - 범위: 만들 것과 만들지 않을 것, 과제가 요구한 제출물과 형식.
   - 완료 조건: 무엇이 실행되고 어떤 값이 나오면 끝인지. 화면이 있으면 사용자가 가장 자주 하는 일 1~2개를 정하고, 그 일을 처음 쓰는 사람이 설명 없이 몇 단계 만에 끝내는지와 주요 버튼과 입력이 실제로 동작하는 것을 포함한다.
3. **방식 비교와 선택**: 방식 2개의 장점, 포기하는 것, 큰 위험, 설명하기 쉬운 정도를 비교하고 하나를 추천한다(비슷하면 설명하기 쉬운 쪽). 고른 뒤에는 그 방식에 대한 가장 강한 반론 한 줄과 답을 남긴다.
4. **위험**: "현장에서 실패했다면 왜일까?"로 3~5개를 찾아 Tiger(대책 없으면 실제 피해), Paper(위험해 보이지만 괜찮음, 이유 한 줄), Elephant(드러나지 않았지만 중요한 우려)로 표시한다. 대책을 세우기로 한 Tiger는 7번의 단계로 넣는다.
5. **예외와 데이터 보호**: 예외 상황(빈 입력, 잘못된 값, 제약 위반, 후보 없음 등)마다 기대 동작을 정하고, 실패했을 때 기존 데이터를 어떻게 지킬지 정한다. 화면이 있으면 오류가 났을 때 사용자가 다음에 할 일을 화면에 보여준다.
6. **화면, 구조, 유지보수**
   - 화면(있을 때): 사용자 기준으로 설계한다. 사용자가 이 화면에서 알고 싶은 것 1~3개를 먼저 정하고, 그것이 첫 화면에서 설명 없이 바로 보이고 이해되게 한다. 사용자가 평소 쓰는 말로 쓰고, 세부와 근거는 필요할 때 펼쳐 보게 한다. 만드는 쪽에 편한 구성(데이터 구조 순서, 내부 용어)은 쓰지 않는다.
   - 모듈 지도: 모듈이나 파일(많아야 8개)마다 맡은 일 한 줄. 입력 하나가 결과가 되는 경로(`파일:함수` 순서), 데이터가 어디에 저장되고 누가 바꾸는지. 계산·판정 같은 핵심 로직은 화면 코드와 분리한다.
   - 유지보수: 제출 뒤 누가 운영하고 고치는지. 자주 바뀔 것(기준값, 규칙, 데이터 형식)과 그것을 어디서 바꾸는지(코드가 아니라 설정 파일 한 곳). 문제가 생겼을 때 담당자가 원인을 알 수 있는 방법(오류 메시지, 기록). 새 담당자가 README만 보고 실행하고 값을 바꿀 수 있게 한다. 핵심 로직에는 고친 뒤 다시 돌려 볼 확인용 테스트를 1~2개 둔다.
7. **작업 단계**: 3~6단계. 단계마다 만들 것과 끝났는지 확인하는 방법 한 줄. 동시에 진행해도 되는 단계는 표시한다.
8. **담당자에게 확인할 것**: 1~7에서 추정으로 채운 것 중 결과를 바꿀 수 있는 것만, 많아도 5개.
9. **설명 질문**: 이 프로젝트에 맞춘 질문 8개. 설계 선택, 구조와 데이터 흐름, 검증 범위, 동작과 예외, 가장 약한 지점, AI와 함께 내린 결정, 사용자 편의, 유지보수에서 하나씩.

## AGENTS.md

아래 블록을 프로젝트 루트의 AGENTS.md 맨 아래에 추가한다(없으면 만든다). 같은 뜻의 줄이 이미 있으면 그 줄은 뺀다. check.md 경로는 이 스킬이 실제로 설치된 위치로 적는다.

```
## 작업 규칙 (explain-check)
- 기능이나 모듈을 새로 만들 때, 핵심 로직이나 예외 처리를 바꿀 때, 완료를 판단할 때는 프로젝트 루트의 EXPLAIN.md(이 파일과 같은 폴더)에서 "설계"를 읽고 따른다(완료 조건, 위험 대책, 예외 동작, 화면, 구조와 유지보수, 작업 단계). 문구나 스타일 같은 작은 수정에는 읽지 않는다. 사용자의 새 지시와 다르면 사용자 지시가 우선이다.
- EXPLAIN.md는 plan을 실행한 세션에서만 고친다. 다른 세션은 기록할 내용을 사용자에게 보여주기만 한다.
- 모호한 점은 가정을 밝히고 진행하고, 커밋 메시지에 `가정:`으로 남긴다.
- 파일 수정, 실행, 테스트, 커밋은 묻지 않고 한다. 요청 범위를 넓히거나 데이터를 지우는 일은 먼저 묻고, 외부 전송과 git push는 사용자가 직접 지시할 때만 한다.
- 단계가 끝날 때마다 무엇을 했는지 알 수 있는 메시지로 커밋한다.
- 핵심 계산·판정 로직이나 모듈 구성을 바꾸면 .agents/skills/explain-check/references/check.md를 따른다.
```
